# Database

SQLite through Python's standard `sqlite3` module. No ORM. The full schema is in `schema.json`.

## Tables

```
users 1──n boards 1──n columns 1──n cards
users n──n boards (board_members: boards shared with other users)
```

- **users** - `id`, `username` (unique, ignoring case since migration 7; stored as registered), `password_hash` (`scrypt$<salt hex>$<hash hex>`, from `app/auth.py`; null only for rows created before accounts existed).
- **boards** - `id`, `user_id` (indexed; a user has any number of boards, at least one), `title`.
- **columns** - `id`, `board_id`, `title`, `position`. Every board starts with the same 5 columns, created with the board. Columns can be renamed, added (at the end, up to 20), reordered and deleted (not the last one); deleting moves the cards to another column or deletes them.
- **board_members** - `board_id`, `user_id` (primary key together; index on `user_id`). Users other than the owner who can open the board. The owner is never a row here.
- **comments** - `id` (`comment-<12 hex>`), `card_id` (cascade), `user_id` (`ON DELETE SET NULL`: a deleted author's comments stay, without a name), `text`, `created_at` (UTC ISO).
- **activity** - `id`, `board_id` (cascade), `user_id` (`SET NULL`), `message` (e.g. `moved card "X" to "Done"`), `created_at`. Written in the same transaction as the change it describes, so a failed change leaves no entry.
- **checklist_items** - `id` (`item-<12 hex>`), `card_id` (cascade), `text`, `done` (0/1), `position` (0, 1, 2, ... within the card, renumbered on delete).
- **cards** - `id`, `column_id`, `title`, `details`, `position`, `priority` (`none`/`low`/`medium`/`high`, CHECK constraint), `due_date` (ISO `YYYY-MM-DD` text or null), `labels` (JSON array of strings; a separate table is not worth it for a few tags per card).

Every access goes through `db.transaction()`, which runs `BEGIN IMMEDIATE ... COMMIT`. The write lock is taken before the first read, so a change sees a consistent board and concurrent changes run one after another (Python's `sqlite3` would otherwise only start the transaction at the first write).

Foreign keys use `ON DELETE CASCADE`, so deleting a user removes their board, columns and cards. `PRAGMA foreign_keys = ON` is set on every connection, since SQLite has it off by default.

## IDs

Columns and cards use text IDs generated by the backend: `col-<12 hex>` and `card-<12 hex>`. They are what the frontend already uses as strings, and the prefixes keep column and card IDs from ever colliding, which the drag-and-drop code relies on (it treats an ID as either a column or a card). The AI also refers to cards and columns by these IDs.

Users and boards use integer IDs. Board ids appear in API paths (`/api/boards/{id}`); user ids stay in the session.

## Ordering

Each card has an integer `position`, kept as 0, 1, 2, ... within its column. Moving or deleting a card renumbers the affected columns inside one transaction. Boards are small, so rewriting a few rows per change is cheaper to reason about than fractional or linked-list ordering.

Column order is `position` 0, 1, 2, ... within the board, renumbered on every add, move or delete. Because of `UNIQUE (board_id, position)`, renumbering first writes temporary negative positions, then the final ones.

## API shape

The backend reads the tables and returns the shape the frontend already uses (`BoardData` in `frontend/src/lib/kanban.ts`):

```json
{
  "columns": [{ "id": "col-...", "title": "Backlog", "cardIds": ["card-..."] }],
  "cards": {
    "card-...": {
      "id": "card-...", "title": "...", "details": "...",
      "priority": "high", "dueDate": "2026-12-24", "labels": ["ux"],
      "checklist": [{ "id": "item-...", "text": "...", "done": false }]
    }
  }
}
```

`cardIds` comes from the cards of that column ordered by `position`.

## Creation and seeding

- The DB file path comes from the `DB_PATH` env var, defaulting to `backend/data/pm.db` regardless of the working directory. In Docker this is `/app/data/pm.db` on the `data` volume, so it survives container restarts.
- On startup the backend creates the parent directory and the tables if they do not exist, then applies pending migrations (see below), so a fresh install needs no setup step.
- Users are created by registration (and the demo account on startup). Registration also creates the user's first board, "My board", with the 5 default columns (Backlog, Discovery, In Progress, Review, Done) and the 8 demo cards; a user who has no boards (an account from before migration 2) gets one when the board list is first read. Boards created later get the default columns and no cards.
- Tests point `DB_PATH` at a temporary file.

## Consequences for later parts

- Seeded IDs are random, so e2e tests find columns by position and cards by title.

## Migrations

`SCHEMA` in `db.py` is the original (version 0) schema and is never edited. Every change since is an entry in `MIGRATIONS`; migration N moves `PRAGMA user_version` from N-1 to N. `init_db()` creates the version 0 tables if missing, then `migrate()` applies the pending migrations, each in its own `BEGIN IMMEDIATE` transaction together with its version bump (the version is read under the lock, so two starting processes cannot both apply one). Foreign keys are off during migrations, so a table can be rebuilt (create new, copy, drop, rename) without cascading deletes, and `PRAGMA foreign_key_check` must be clean before the commit. Fresh and existing databases take the same path, so every test exercises the migrations.

| Version | Change |
|---|---|
| 1 | `users.password_hash` |
| 2 | `boards` rebuilt without `UNIQUE(user_id)`, with `title` (existing boards keep their id and get "My board"), index on `user_id` |
| 3 | `cards.priority` (default `none`), `cards.due_date`, `cards.labels` (default `[]`) |
| 4 | `board_members` table |
| 5 | `comments` and `activity` tables |
| 6 | `checklist_items` table |
| 7 | Unique index on `username COLLATE NOCASE` (usernames ignore case). Refused, leaving the database at version 6, if two names differ only in case |

To change the schema, append a migration (plain SQL statements; no semicolons inside string literals) and add a test that upgrades a database holding data from the previous version.
